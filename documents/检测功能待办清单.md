## 🚧 待补充的检测项

### 1. 🔊 音量响度检测（LUFS）— 优先级：高

**问题描述：** 目前完全没有检测音频的响度水平，而这恰恰是本工具的核心功能。

**实现方案：**
```bash
# 使用 ffmpeg 的 ebur128 滤镜分析响度
ffmpeg -i input.mp3 -af ebur128=peak=true -f null -
# 从 stderr 中解析 integrated loudness (I), true peak (TP), loudness range (LRA)
```

**检测阈值建议：**
- `loudness_too_low`: integrated < -30 LUFS（声音太小）
- `loudness_too_high`: integrated > -6 LUFS（声音太大，可能削波）
- `true_peak_clipping`: true peak > 0 dBTP（削波失真）

**代码位置：** `scanner.py` → `analyze_mp3()` 中新增 `ebur128` 分析

**注意事项：**
- ebur128 分析比 ffprobe 慢得多（需要解码整个文件），建议作为可选步骤
- 可以用 ffprobe 的 `volumedetect` 滤镜作为快速替代（精度较低）

---

### 2. 🔇 异常短时长检测 — 优先级：高

**问题描述：** 当前只检测 `duration == 0`，但实际中很多损坏文件时长极短（如几秒的铃声、截断的录制片段）。

**实现方案：**
```python
# 在 detect_issues() 中新增
if 0 < file_info["duration"] < 30:
    issues.append("abnormal_short")  # 不到30秒，可能是截断或铃声
```

**检测阈值建议：**
- `very_short`: 0 < 时长 < 10 秒（极可能是损坏/截断）
- `short_track`: 10 ≤ 时长 < 30 秒（短曲/铃声，需人工确认）

---

### 3. 🎵 文件完整性验证 — 优先级：中

**问题描述：** 目前只用 ffprobe 读元数据，没有尝试实际解码音频数据。元数据正常不代表音频数据没损坏。

**实现方案：**
```bash
# 尝试完整解码，检查是否有解码错误
ffmpeg -v error -i input.mp3 -f null - 2>&1
# stderr 中出现的 error/warning 即为问题
```

**检测标识：**
- `decode_error`: 解码过程中出现错误
- `truncated_file`: 文件不完整（解码提前结束）
- `corrupt_frame`: 存在损坏的音频帧

**注意事项：**
- 此检测需要完整解码，速度较慢，建议标记为可选
- 可结合 `progress_callback` 显示进度

---

### 4. 📊 编码模式检测（VBR/CBR）— 优先级：低

**问题描述：** 未检测音频的编码模式。VBR（可变比特率）文件的比特率显示可能不准确。

**实现方案：**
```bash
# 通过 ffprobe 检测
ffprobe -v quiet -print_format json -show_format input.mp3
# 查看 format.bit_rate 是否为 "N/A"（通常表示 VBR）
```

**检测标识：**
- `vbr_file`: VBR 编码文件（比特率显示为平均值）

---

### 5. 🏷️ 元数据/标签完整性 — 优先级：低

**问题描述：** 未检测 ID3 标签是否缺失或损坏。缺少标签的文件在播放器中显示为"未知艺术家"。

**实现方案：**
```bash
ffprobe -v quiet -print_format json -show_format input.mp3
# 检查 format.tags 是否存在，以及 title/artist/album 等关键字段
```

**检测标识：**
- `missing_tags`: 完全没有 ID3 标签
- `incomplete_tags`: 缺少关键字段（title, artist, album）

---

### 6. 🔄 重复文件检测 — 优先级：低

**问题描述：** 同一首歌可能存在多个副本（不同比特率、不同目录），浪费存储空间。

**实现方案：**
- 基于文件大小 + 部分内容哈希（MD5/SHA256）快速匹配
- 或使用 `ffmpeg` 的 `astats` 滤镜比较音频指纹

**检测标识：**
- `duplicate_of`: 标记与哪个文件重复

## 💡 架构建议

当前 `scanner.py` 的 `analyze_mp3()` 是同步逐文件处理，当加入 LUFS 分析等耗时操作后会明显变慢。建议：

1. **分层扫描**：快速扫描（ffprobe 元数据）+ 深度扫描（ebur128 响度分析）可分开触发
2. **增量支持**：记录文件的修改时间和大小，跳过未变化的文件
3. **并行处理**：使用 `concurrent.futures.ProcessPoolExecutor` 多进程加速
